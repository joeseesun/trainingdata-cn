《AutoGPT 从爆红到沉寂，LangChain 创始人把 Agent 的门槛讲透了》

2023 年春天，AutoGPT 在推特刷屏，一度成为 GitHub 历史上最热门的项目之一。一年多后，普林斯顿团队的 SWE-agent 论文给出一个冷静的数字：编程 Agent 能解决 12.5% 的真实 GitHub 问题，纯 RAG 检索时代的成绩只有 3.8%。进步巨大，但 12.5% 的水平，连一个实习生都替代不了。这一年发生了什么，Agent 的路到底该怎么走，LangChain 创始人 Harrison Chase 在红杉播客 Training Data 里把这件事拆开讲了一遍。

Harrison 是 Agent 生态里绕不开的名字。红杉合伙人 Pat Grady 称他为「最早把 LLM 和工具、动作连起来的产品远见者」，他创办的 LangChain 是目前 AI 圈最流行的 Agent 开发框架。这期节目从 Agent 的定义聊到认知架构、UX 和 LangChain 的产品版图，几乎是一份 Agent 领域的入门纲要。

Agent 的定义：让 LLM 决定控制流

Agent 这个词被用得太滥，Harrison 给了一个干净的定义：Agent 就是让 LLM 决定应用程序控制流的东西。他拿传统 RAG 链做对比：先生成搜索词，再检索文档，最后生成答案，每一步都提前写死。换成 Agent，LLM 自己决定要不要搜索、搜一次还是搜三次、什么时候直接回答用户。

工具使用和记忆经常被拿来定义 Agent，Harrison 认为它们是配套。LLM 要决定做什么，主要手段就是调用工具；要决定下一步，就得记住自己做过什么。核心始终是控制流。

他强调 Agent 是一条光谱。最简单的一端，LLM 只做一个路由分类，决定走哪条路；最激进的一端是完全自主的 Agent；中间有大量灰色地带。Pat Grady 追问，Agent 的本质是决策还是行动？Harrison 的回答是两者绑在一起，行动的难点恰恰在于决定该做哪个行动，解决了决策，行动自然就通了。

聊到行业从 copilot 走向 Agent 的大判断，Harrison 基本同意。他的理由是，copilot 依赖人在环里，外部系统能替人完成的工作量存在上限；Agent 自己干活，干完再来找你确认，杠杆大得多。他也承认这里有个悖论：放手的越多，产出越大，出错的风险也越大，找到平衡点会是接下来最有趣的设计问题之一。

LangChain 自己的定位也随这条光谱演化。项目早期只有 chains 加一个 AgentExecutor 类，后来发现用户要的控制远比一个类能给的多，于是重投入做了 LangGraph，专门服务中间地带的可定制 Agent。Harrison 把 LangChain 的角色概括为编排层（orchestration layer）。

AutoGPT 为什么凉了

Harrison 回顾了 Agent 的炒作周期：2023 年春夏，AutoGPT 拉开序幕；夏末到 2024 年初是一段低谷；2024 年开始，真实的东西陆续上线。他点了几个名字：Elastic 把助手和 Agent 放进了生产环境，还在 RSA 安全大会上发布了新东西；Klarna 的客服机器人引发大量讨论；Devin 和 Sierra 这些公司也冒了出来。

AutoGPT 式架构的问题，Harrison 说得很直接：它太通用、太不受约束，这让它激动人心，也让它没法干活。真实业务里，人们想让 Agent 做的是非常具体的任务，遵守明确的规则，按特定的方式做事。全自主的原型几行代码就能跑起来，但要产生业务价值，就得写大量定制逻辑，反复试出什么有效什么无效，工程量完全不同。

他为此造了一个词：认知架构（cognitive architecture）。意思是从用户输入到输出，数据、信息和 LLM 调用是怎么流动的。有没有分支，有没有循环，哪些步骤用算法，哪些步骤让模型推理。把这套流程画成图，就是这套 LLM 应用的系统架构。Harrison 观察到，真正上了生产的 Agent，画出来几乎都是定制化的图，因为每个业务都有自己的检查点、子步骤和回环。叫它「认知架构」，是因为这本质上是把人类做任务的思考模型，编码进软件系统。

红杉的索尼娅·黄（Sonya Huang）引用普林斯顿的数据追问：12.5% 对 3.8%，进步巨大，但离替代实习生还很远。Harrison 的回应是分场景看。SWE-agent 是相对通用的 Agent，被要求跨各种 GitHub 仓库工作；Vercel 的 v0 这类深度定制的 Agent，可靠性远超 12.5%，已经能上生产。通用 Agent 依然很难，更长的上下文、更好的规划和推理会帮到它们，但今天能干活的，基本都是定制的。

从思维链到 ReAct：架构是怎么进化出来的

今天的认知架构，是被早期的问题一步步逼出来的。Harrison 梳理了这条线。最早，LLM 连第一步该做什么都推不清楚，思维链（chain of thought）这类提示技巧给了模型逐步思考的空间，后来这个能力被直接训练进模型，成了默认行为。

然后是普林斯顿研究者姚顺雨（Shunyu Yao）的 ReAct 论文，Harrison 称它为「第一个面向 Agent 的认知架构」。它在每一步行动前加了一个显式的推理环节，然后放进循环里跑。有意思的是，等推理能力被训练进模型，那个显式的推理步骤正在变得多余，今天很多人做 ReAct 风格的 Agent，直接用函数调用，不再保留原论文里的思考文本，留下来的只是那个循环。

循环跑起来之后，暴露出两个核心难题：规划和收尾。规划指模型难以制定好的长期计划，并在循环中追踪进度；收尾指模型做完一步就可能宣布完工，哪怕计划还有四步没走。对应的架构解法也直接：先让模型显式生成一个计划，再逐步执行；做完动作后，加一个显式的反思环节，让模型判断自己是否真的做对了，搜索结果很差就重来，别把垃圾答案直接返回给用户。规划和反思是两个最流行的通用架构，Harrison 预计它们会逐步被训练进模型，但定制架构里那些和业务逻辑绑死的控制流，永远不会。

Pat Grady 抛出了全场最尖锐的问题：这种定制加硬编码的路线，是方向，还是过渡方案？Harrison 先承认一个极端论证成立：如果模型的规划能力强到足够可靠，最好的架构可能就是一个 for 循环，调模型、做决策、执行、再循环，所有约束全写进 prompt。他给出两条反对理由。第一是效率，既然已知 A 之后必须做 B，直接把顺序排好就行，没必要每次都让模型重新想。第二是可靠性，LLM 是非确定性的，企业场景需要保证该先做 A 的地方永远先做 A。

然后他抛出一个自认的热观点。把认知架构按「通用还是定制」「简单还是复杂」分两个轴，会得到几种组合：简单又通用的 for 循环，生产里定制又复杂的架构，还有一类复杂但通用的架构，比如复杂的规划步骤、反思循环、思维树。Harrison 判断，复杂但通用这一类会逐渐消失，因为通用的规划和反思会被直接训练进模型。但定制又复杂的那一类永远存在，领域知识、业务流程、非通用的控制逻辑，不管模型多强都不会被内置。他对光谱的两端都看好。

Harrison 在这里分享了一个贝索斯的引用。20 世纪初的啤酒厂流行自己发电，贝索斯提醒创业者，专注在能让啤酒更好喝的事情上。这个类比放到今天，问题变成了：掌握自己的认知架构，能不能让啤酒更好喝？他的答案分两半。通用认知架构不让啤酒更好喝，通用规划、通用反思，模型厂商会做，开箱即用的方案会越来越多。但定制认知架构绝对让啤酒更好喝：把客服团队思考问题的方式、内部业务流程、某类代码的最佳实践编码进系统，当应用开始替人干活时，这套定制逻辑就是卖的核心东西。UI、UX 和分发仍然重要，但通用和定制的界线要画清楚。

UX 是架构的一部分

这是 Harrison 花时间最多的话题之一。他的核心判断是：UX 能直接影响架构的有效性。LLM 还不完美，会犯错，所以聊天成了当前的主导 UX：输出流式可见，随时可以纠正和追问。但聊天的代价是人一直在环里，本质还是 copilot 模式，上限受限。

他列了几个正在出现的模式：

  • 透明清单加回滚。Devin 把 Agent 做过的每件事列出来，看到第三步错了，可以回滚到那里，改指令或者手动改决策，再继续跑。
  • 收件箱。十个 Agent 并行在后台跑，遇到需要人拍板的地方就发消息求救，人像处理邮件一样处理它们的问题。
  • 审阅工作流。Agent 写初稿，人留评论，Agent 一次性修完。研究型项目 GPT Researcher 是很好的试验场。更进一步的版本是 Google Docs 式的人机同时协作，人留一条评论，Agent 修一条，再留下一条。
  • 从反馈中学习。同一条反馈让人重复一百遍是不可接受的，系统架构必须让 Agent 能记住纠正。

这些都还在早期，Harrison 说团队花了大量时间想这些问题。

旧工具哪里够用，哪里要造新轮子

LangChain 的产品版图分三层：开源框架负责标准化各种模型、向量库、工具的接口；LangGraph 处理带循环、需要持久化、支持异步和人在环的编排；LangSmith 从公司创立起就在做，负责可观测性和测试，外加 prompt 管理和人工标注队列。

Pat Grady 问了一个好问题：哪些地方旧工具够用，哪些地方必须造新轮子？Harrison 的判断是可观测性明显需要新东西。Datadog 这类工具的单条链路监控很强，但多步 LLM 应用需要跨 trace 的洞察，而开发者恰恰因为非确定性要反复看单条 trace 排错。测试侧的差异更根本，他列了三点：

  • 成对比较。传统软件测试只判断通过或失败，LLM 评测最受信任的方式是 LMSYS 竞技场式的两两对比。
  • 通过率永远到不了 100%，重点变成追踪它随时间的走势，确保没有回退。
  • 人在环。软件能判断 2 等于 2，人看一眼也是同样的结论；LLM 的输出质量，很多时候只有人能评。

顺带回应了微调和 prompt 的关系。Harrison 不认为它们互相替代，反而互补：认知架构越定制，每个节点的任务范围就越窄，窄任务恰恰是微调最甜的场。至于 LangChain 不碰的领域，模型层、向量数据库、微调基础设施有 Fireworks 这样的公司在做；他还列了一串 Agent 经济时代才会出现的机会：Agent 的身份验证、权限管理、支付，甚至 Agent 付钱请人做事。

So what，以及明天就能用的四条

红杉创始人 Don Valentine 以爱问「so what」出名，Pat Grady 把这个问题抛给了 Harrison：假设自主 Agent 完美运转，世界会怎样？Harrison 的回答是，大量重复性工作被自动化，人类去做更高杠杆的事。他给了一个具体画面：一个人扮演 CEO，配一个营销 Agent、一个销售 Agent，把原本要招人的职能全部外包出去，自己专注战略和产品思考。今天已经有牵引力的领域有两个：客服，影响已经发生；编程，热度很高但成熟度落后。编程的意义他讲得很动人：他妈妈有一个网站创意，但不会写代码，如果 Agent 能补上执行，她就能专注在想法本身。Pat Grady 补充，这正是 Figma 的 Dylan Field 常讲的主题，缩小从梦想到现实的差距。生成式 AI 时代做建设者的门槛变了，能造东西的人群会大幅扩大。

闪电问答里还有些轻松的料。他最佩服 OpenAI 过去一年半的执行力，也点名了研究员 David Dohan，说此人早期关于模型级联的论文深刻影响了他思考问题的方式；他还佩服扎克伯格和 Meta 押注 Llama 与开源的姿态。问到自己的领导风格，他自认是产品型 CEO，参考对象是 Airbnb 的 Brian Chesky。

给创业者的建议，Harrison 只有一句：

「Just build，去动手做。GPT-5 会出来，它可能会让你做的某些东西变得不再相关，但你会在这个过程中学到太多东西。我强烈地相信这是一场变革性的技术，你学得越多越好。」

Pat Grady 补了个细节：2023 年初红杉第一届 AI Ascent 会议，Harrison 坐在台下听了一整天演讲，同时推了一整天代码，那天正好 OpenAI 发布插件。他显然严格执行了自己给的建议。

这期节目能直接提炼出四条明天就能用的东西：

  • 判断该用链还是 Agent，看控制流。步骤固定就写死代码，只有需要 LLM 现场决定路径时才引入 Agent，路由分类也算 Agent 的最低配。
  • 别追求全自主。把规划做成显式步骤，把「检查自己是否做对了」做成显式的反思环节，AutoGPT 的教训是约束越少越没用。
  • 上生产之前先上可观测性和评测。追踪通过率趋势，建人工评审队列，接受通过率到不了 100% 这个前提。
  • 把精力花在定制认知架构上，编码团队独有的业务逻辑和思考方式，通用规划能力交给模型厂商去卷。

AutoGPT 的故事讲完了，Agent 的故事才刚开始。用 Harrison 自己的话说，现在还特别早，有太多东西等着被造出来。
