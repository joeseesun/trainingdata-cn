《LangChain 创始人：智能体第 14 步的上下文，代码里看不到》

2025 年 6 月到 7 月，LangChain 团队注意到一件怪事。Claude Code 火了，Deep Research 火了，Manus 也火了。扒开看，这三个产品底层跑着同一套算法：一个 LLM 在循环里，自己决定下一步干什么。这套算法一点都不新，AutoGPT 两年前就是这么干的，火了一阵就哑火。这次的区别只剩一个：上下文工程（context engineering）的水平。

发现这一点后，LangChain 立刻立项做了 Deep Agents。2026 年 1 月，创始人 Harrison Chase 带着这套判断再上红杉播客 Training Data。他是这档节目开播以来的第一位嘉宾，主持人 Sonya Huang 提醒他，18 个月没见，行业已经翻了好几轮。Harrison 回得很轻松：「我会再告诉我妈一次，我又上播客了。」

这场对话信息密度极高，把智能体行业这两年的底层变化基本讲透了。挑最值钱的部分展开。

长时程智能体终于能用了，但杀手用法是「初稿」

红杉刚发了一篇博客，把这一波产品叫 long-horizon agents，长时程智能体：给智能体一个任务，它能连续干几个小时甚至几天。Harrison 认可这个判断。让 LLM 在循环里跑、完全自主决定做什么，这个念头从智能体概念诞生第一天就有。之前不行的原因很简单：模型不够好，外面的脚手架也不够好。现在两块都补上了。

但能用，不等于能当全自动员工使。Harrison 给了一个很清醒的判断：智能体的可靠性离所谓 nine nines，也就是 99.9999999% 的水平，差得远。它能干大量的活，干活时间越来越长，可结果必须有人看一眼。

所以他总结的杀手级用法，三个字：出初稿。

  • 写代码：智能体提交 PR，人审完再合并，不直接推生产环境。
  • AI 运维（SRE）：红杉投的 Traversal 做这个，智能体翻日志查事故，产出报告交给人复核。
  • 研究报告：智能体生成初稿，人编辑后再发出去，金融行业已经在大量这么用。
  • 客服：Klarna 在用的人机协作，第一线 AI 接不住就升级给人工，同时后台的长时程智能体把事件全过程整理成报告，交接给人工客服。

共同点很清楚：找一个能跑很久、产出一份初稿的任务形态，人只做最后一道审核。这是当下长时程智能体最稳的产品结构。

模型、框架、挽具，三层到底差在哪

这场播客里最有信息量的概念拆解，是 Harrison 对三个词的区分。

模型，就是 LLM 本体，token 进 token 出。框架，是围绕模型的抽象层，方便换模型、接工具、接向量库，对里面装什么不表态，LangChain 早期就是这个定位。挽具（harness），自带电池的成品：默认装好规划工具、上下文压缩、文件系统工具，每个设计决定都是明确的观点。

LangChain 现在的 Deep Agents 就是一个挽具，跑在自家的 LangGraph 框架上，默认内置规划工具，这本身就是表态：长任务就该先规划。

挽具和模型是共同进化的。两年前没人知道基于文件系统的挽具是最好的做法，因为当时的模型没怎么在这类数据上训练过。现在不一样了，OpenAI 的模型重度训练 Bash，Anthropic 的模型配了专门的文件编辑工具。挽具要贴着模型家族的训练数据来设计，给 Claude 用的挽具和给 GPT 用的挽具，细节就该长得不一样。

一个有意思的事实：Claude Code 之所以火，Harrison 认为很大一部分功劳在挽具本身。证据是 Terminal-Bench 2.0 这个编程基准，它把模型和挽具分开列成绩，Claude Code 并不在榜首。做编码产品的公司几乎全在自研挽具，Factory 和 Amp 的挽具都被他点名称赞。

挽具工程难在哪？Harrison 给了一个很具体的失败案例：主智能体派子智能体干活，子智能体干完，只有最终回复传回主智能体。他们见过子智能体干了一大堆活，最后回一句「看我上面的工作」，主智能体根本看不到那些内容，直接懵了。挽具里那些几百行的提示词，干的活就是教这几个组件怎么互相交接。

还有一个趋势值得记下：以前要在代码里给模型加的结构，现在很多挪进了工具和自然语言指令里。复杂度没有消失，只是换了语言，所以改提示词、甚至自动更新提示词，正在变成工程的一部分。

三个时代，一个拐点

主持人 Pat Grady 问：过去五年，模型侧的拐点是 ChatGPT 和 o1，那模型外围的工程侧，拐点在哪？

Harrison 把这几年分成三个时代。第一个时代，LangChain 刚创立，模型还是纯文本进纯文本出，没有工具调用，没有推理，大家能做的只有单条提示词和简单的链。第二个时代，模型厂商把工具调用训练进模型，模型勉强能决定下一步做什么，但不够聪明，得靠自定义认知架构，在代码里显式问模型「这里该怎么办」，走分支、加循环，脚手架越搭越厚。

第三个时代的拐点，他定在 2025 年年中。Claude Code、Deep Research、Manus 同时起飞，底层全是同一个循环算法，赢在上下文工程的细节上。编程社区的体感拐点稍晚，是 Opus 4.5 发布那阵，正好赶上寒假，大家回家重度使用 Claude Code，才发现它真能啃硬骨头。到 11 月、12 月，他感觉整个行业完成了一次明显的情绪转向。

他的原话：「模型在某个时间点终于够好了，那就是我们从脚手架转向挽具的时刻。」

下一站是什么？他给了一个方向：把更多手动环节交给模型自己。现在上下文压缩还是挽具作者手动设计的，Anthropic 已经在试让模型自己决定什么时候压缩，用的人还不多。另外就是记忆，他把它定义为「跨更长时间的上下文工程」，本质还是给 LLM 喂对上下文，只是时间尺度拉长了。

造智能体和造软件，差在哪

「造智能体跟造软件不一样」这句话已经说烂了，Harrison 承认自己听多了都翻白眼。所以他专门写文章拆过，到底哪里不一样。答案有两层。

第一层，逻辑的位置变了。软件的全部逻辑写在代码里，看代码就知道程序会干什么。智能体的逻辑，一大半在模型那几十亿个参数里。想知道智能体在某个场景会做什么，唯一办法是跑起来看。真相来源变了：软件看代码，智能体看代码加轨迹（trace）。

他给了一个特别形象的说明。单次 LLM 应用出了坏结果，你知道提示词是什么、上下文是什么，都是代码定死的。智能体是循环执行，第 14 步的上下文里装了什么，没人知道，因为前面 13 步每一步都可能往里塞东西。所以轨迹在智能体开发里的地位，远高于传统软件的日志：软件日志出了错才开，智能体轨迹从第一天就要盯。

「上下文工程这个词太好了，我真希望是我发明的。它其实描述了我们在 LangChain 做过的所有事，只是当时这个词还不存在。」

这个变化已经改写了团队协作。以前出了问题，同事说「去看看 GitHub 上的代码」。现在 LangChain 的开源项目收到用户反馈，说 Deep Agents 跑飞了，官方回复是：把 LangSmith 轨迹发过来，没有轨迹没法帮你查。测试也跟着变：测试用例从轨迹里提炼，线上测试的重要性超过线下，因为智能体的真实行为，只有喂了真实输入才会暴露。

第二层，迭代方式变了。软件也讲迭代，但软件上线前你就知道它干什么，迭代的是用户要不要。智能体上线前，没人知道它到底会干什么，得一轮轮跑、一轮轮改提示词，才能逼近可用。Harrison 算过这笔账：开发者为了调对行为，改系统提示词的次数远超改代码的次数。记忆的价值就在这，让系统自己从交互里学，替开发者省掉一部分迭代。

顺带回答了一个所有人都关心的问题：谁来造智能体？人的层面，LangChain 内部的应用团队明显偏年轻，行业里智能体工程团队也普遍是资历更浅的开发者居多，因为他们没有旧软件的先入之见。但很多资深开发者也拥抱了智能体编程，连 Pat 都被 Sonya 拉着用上了 Claude Code，所以归根结底是心态问题。

公司层面，他给传统软件公司指了条路：数据和 API 的价值在涨。一位金融行业的人士告诉他，数据的价值一路飙升。老公司只要把数据和高质量的 API 接到智能体上，就能吃到红利。缺的是另一块：怎么用这些数据的指令。以前这些活是人干的，公司从没把它固化成知识，这块是净新增。所以像 Rogo 这样懂金融的团队，把行业知识灌进智能体，反而跑得快，因为智能体的表现高度依赖「这类活具体怎么干」的知识。

评估、裁判，和智能体自己修自己

软件测试靠断言，机器判断对错。智能体干的是人干的活，判断好坏得引入人的判断。LangSmith 做的事之一，就是把人拉进轨迹里标注：说这句好那句差、应该怎么做，甚至直接摆出正确步骤。数据标注创业公司这两年生意很好，就是这个原因。

纯靠人标太贵，所以要用 LLM 当裁判做代理。关键在校准：裁判跟人的判断对不上，整个评估就废了。LangSmith 有个叫 align evals 的功能，人先标一批轨迹，再用这批标注校准出一个 LLM 裁判。

评估数据拿来干什么？Harrison 给了一个他个人非常看好的模式，比给应用公司上强化学习更看好：让编码智能体顺着轨迹去修智能体。LangSmith 做了 MCP 接口和一个命令行工具，交给 Claude Code 这类编码智能体，它就能拉下轨迹、诊断哪里出了问题、回到代码库里改。改完人审一遍，保证不跑偏。一个带人监督的递归自我改进循环，已经在真实运转。

更进一步的版本是刚发布的 Agent Builder，无代码建智能体，自带记忆。用户对智能体说「下次别这么干，应该那么干」，它会自己去改自己的指令文件。Harrison 想加的下一个功能：每天夜里跑一个任务，把当天的轨迹全看一遍，更新自己的指令。他引用了圈子里一个传神的说法，sleep time compute，睡觉时计算。白天干活，晚上做梦复盘。

聊到记忆，他先泼了盆冷水。ChatGPT 加了记忆，他几乎不用，也没觉得更离不开这个产品，因为他去 ChatGPT 问的都是一次性的问题，问软件、问吃的、问旅行，很少重复自己。但换成具体工作流，结论完全反过来。他有一个跑了两年、一直在给 Sonya 发邮件的智能体，想迁进 Agent Builder。迁过去之后，启动提示词一样，工具一样，就是记忆没带过去，体验明显变差，他到现在都没完成迁移。提示词谁都能抄，工具谁都能接，记忆带不走，这就是护城河。

文件系统、沙箱、界面：智能体的标配清单

被问到每个智能体是不是都该配沙箱、配电脑、配浏览器，Harrison 的态度分了三档。

文件系统，他是彻底的信徒，原话用了 file system pilled 这种说法。他的判断很硬：现在做长时程智能体，必须给它文件系统。理由全跟上下文管理有关：压缩上下文时，把原始消息全存进文件系统，需要时再查；工具返回的大结果不塞给模型，落盘让它按需读。没有真文件系统，可以用虚拟文件系统顶着，更省资源，但虚拟的没法跑代码，写脚本处理数据这种事替代不了。

代码执行，他给了九成信心。重复性高的任务可以少用代码，但长尾任务里写代码没有替代品。浏览器使用，他直接说模型现在还不够好，顶多给编码智能体配个命令行工具凑合。计算机使用是两者的混合体，介于中间。

顺带回应了行业里吵了很久的问题：编码智能体是不是所有智能体的子类？他的说法很绕但很准：通用智能体可以是编码智能体，但今天的编码智能体不等于通用智能体，因为它们全是为编码任务调优的。这是 LangChain 现在想得最多的问题之一。

界面这块，他的判断是长时程智能体需要同步加异步两种模式。任务要跑一天，人不可能干等着，得能同时挂好几个任务，像管看板一样管它们，Linear、Jira、邮件都是可以借鉴的管理界面。但智能体交回一份研究报告，人得指出哪里写错了，这时候要切回同步聊天。

他们一年前发布过 Agent Inbox，第一版只有异步：智能体发来消息，人回一句，然后干等下一条。后来加了一个改动，打开收件箱直接进入聊天界面，就这一个同步入口，体验完全解锁。他现在的结论是：纯异步模式目前跑不通，人会一直在同步和异步之间来回切。

还有个细节值得抄。Anthropic 发布 Claude Cowork 时，让用户选一个工作目录，等于告诉智能体「这是你的工作区」。工作区可以是 Google Drive，可以是 Notion 页面，任何存状态的地方。人和智能体围绕同一个状态协作：异步派活，同步聊天，顺便查看它改了什么。

明天就能用的五件事

这场对话听着都是行业判断，拆出来全是动作。

  • 智能体应用还没接轨迹工具的，今天就接。别等出事再开日志，轨迹要从开发第一天就开着看，它是唯一能看清第 14 步发生了什么的窗口。
  • 给长时程智能体配文件系统。压缩上下文时保留原始消息的存档，大工具结果落盘按需读取，对长任务的稳定性提升立竿见影。
  • 产品设计上找「初稿」形态。让智能体产出 PR、报告、草稿，人做最后一审，先别急着做全自动。
  • 用 LLM 当裁判可以，但先用人标几十条轨迹校准它。裁判歪了，整个评估体系都在自欺欺人。
  • 把编码智能体接进运维工具链，让它拉轨迹、查故障、提修复，人只审结果。这是当下性价比最高的递归改进，不用训练任何模型。

节目最后，主持人夸 Harrison 一直在提前看到智能体的未来。他的收尾很实在：「我期待未来再上一次节目，到时候我今天的预测全错。」预测未来这件事，确实难。
