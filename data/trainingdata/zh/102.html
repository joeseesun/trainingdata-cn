《Anthropic 平台一年长出三层：从一条 API 到给 token 分工》

一年前，Katelyn Lesse 加入 Anthropic 的时候，整个开发者平台基本就是一条 Messages API。无状态，调完即走，配上 SDK 和文档，就这些。

一年后，这个平台上跑着托管智能体、自托管沙箱、技能和记忆标准，最上面还长出一层叫「策略」的新东西：token 不再是均质的燃料，每个 token 都能领到一份具体工作，有的负责执行，有的负责出主意，有的干完活还要被打分重来。

这是红杉资本播客 Training Data 最新一集的内容，嘉宾是 Anthropic 平台的两位负责人：Katelyn Lesse 和 Angela Jiang。对外，这个平台是所有开发者接入 Claude 的 API 和工具；对内，它是 Claude 自家产品脚下的地基。Katelyn 之前在 Stripe，管过那份让全公司紧张的 AWS 账单。主持人 Sonya Huang 的开场定位是：这可能是世界上最重要的开发者平台，没有之一。

有意思的是，这个团队有两个北极星。Angela 自己也承认这不合常理，但理由很清楚：内部那条，是给自家团队最大的杠杆，让他们快速把「AGI 味十足」的产品发出去，速度是刻意追求的；外部那条，是让任何开发者都能用 Claude 造自己想造的东西，所以平台要贴着业务走，他们会花大量时间和 AWS、Google 这些云厂商做集成。

两个北极星底下压着一条铁律：内部团队和外部开发者用同一套原始件（primitives）。很多平台公司会把内外两套拆开做，Anthropic 刻意不拆。理由是模型能力涨得太快，形态根本定不下来，两年前所有人说「一切皆 chat」，现在所有人说「忘掉 chat，全是 agent」，下一个形态是什么没人知道。他们的办法是内部先吃自己的狗粮，同时开放外部早期访问，两边收反馈，避免偏科。

三层蛋糕：知识、执行、协调

Angela 把平台画成一个三层蛋糕。

  • 知识层：Messages API 的参数形状、工具标准、技能（skills）、记忆（memory），还有 MCP。这一层解决「Claude 知道怎么干活」。
  • 执行层：光知道不够，模型得真的动手，改文件、跨系统操作、跑长任务。这一层是低层 harness 加托管基础设施，比如带治理和安全的沙箱、能暂停再恢复的会话存储，对应产品是 Claude Managed Agents。
  • 协调层：还在成形，Angela 叫它 strategies，一个「元 harness」。核心想法是给不同的 token 分不同的工作：这个执行，那个给大模型当顾问，还有的专门「做梦」，或者干完活被一个打分员检查，不合格就重来。

路线图就藏在这个结构里：抽象层会一路从知识层走向执行层，再走向协调层。

为什么要往上盖？Katelyn 给了个很实际的理由。模型越来越能跑长任务、处理大上下文，客户在反复解决同样的问题，Anthropic 内部也在反复解决同样的问题：怎么起一个合规安全的沙箱，怎么存会话让人随时回来续上，怎么管缓存、管成本。与其让每个客户自己拼积木，不如把 Anthropic 踩过的坑打包成现成的抽象。

顺带说一句，现在的 Managed Agents 其实没那么「高层」，工具、技能、系统提示、MCP 服务器全都开放配置，旋钮很多。她们的终局想象是：告诉智能体你要什么结果、预算多少，然后放手。

客户的分化也很清晰。AI 原生创业公司直接拿原始件自己折腾，他们享受在底层爬坡；其他企业更愿意买打包方案，拼装工作流本来就不是他们的核心竞争力，他们要的是给用户独特价值。

不建围墙花园：跑在谁的服务器上，他们不在乎

单集标题里那句「建生态，不建围墙花园」，Katelyn 用几个具体动作做了注解。

Claude Managed Agents 支持自托管沙箱，Anthropic 跟 Modal、Vercel、Cloudflare，甚至亚马逊新推出的微型虚拟机都做了合作，任何一家的基础设施都能插进来。他们还发了 MCP tunnels，让企业能穿透防火墙，调用自己内网里的 MCP 服务器。

「跑在我们的基础设施还是别人的基础设施上，我们其实并不在意。」

Katelyn 补了半句：他们真正在意的是架构，智能体怎么搭才强大、可靠、可扩展，这件事他们有强烈观点，开发者只要对齐接口就行。Angela 提到 skills 和 MCP 这类标准时说得更干脆：Claude 要有用就得有这些东西，那就直接开放给生态，跟所有人一起建。

她把这套逻辑比作电。有电之前，人类靠蜡烛，能干的事有限。电之所以成为改变一切的公共事业，是因为它能接进所有东西，人人都能用，还有标准插座。这件事没有任何一家公司能自己干成，必须跟整个生态一起把路修出来。

生态里已经有人跑出了花样。Katelyn 讲了一个客户案例：这家公司在 Managed Agents 上建了一批智能体，又在别的模型和平台上建了另一批，各自优化到最强。然后他们冒出一个想法，给其中一个智能体暴露一个 MCP 服务器，让另一个智能体把它当工具来调用。Anthropic 团队坐下来跟他们一起过了一遍，跑通了。智能体调用智能体，这件事已经发生。

还有一类客户在跟老软件搏斗。医疗行业的客户说，我们的系统连 API 都没有，那都是奢望。于是他们用 computer use 去做自动化和连接，有人拿一台笔记本电脑跑一堆东西，自动生成智能体能用的接口。Angela 看下来的结论是：眼下最让人兴奋的创新，大量发生在上下文和连接这一层。有客户给自己搭了定制的软件开发生命周期，有客户把整个后台职能自动化，各种上下文流式灌进智能体的细节非常讲究。这类创新没长成什么新产品形态，全部体现在「对用户有用到极致」上。

Claude Tag 被骂「Slack 机器人」？重点全在水下

Anthropic 自己做产品有两条线。第一条是形态实验。Claude Design 是个例子，表面看像进军设计领域，实际是在验证两个假设：一是能不能把更多事情直接丢给 Claude，少编辑、多对话；二是代码能不能取代传统的所见即所得设计工具，让 Claude 直接生成代码来做设计。早期实验发现，还真行。这些实验来自他们的 labs 团队，很多项目内部酷两周就翻篇，大部分根本不会发布。

第二条是真看 TAM。他们挑领域有个共同标准，Angela 叫它 token hungry：一轮干完，用户的反应是「太爽了，我要再来一轮」。编程就是典型，干完一轮你觉得被解锁了，想建更多东西；有的服务干完一轮任务就结束，这种兴趣不大。已公开的垂直化方向是金融和法律，最近发了 Claude for Financial Services，打包了技能包，还配了教人用 Managed Agents 做金融任务的 cookbooks。

打包思路的代表作是 Claude Tag。发布的时候外面吵翻了，说这不就是个 Slack 机器人吗。类似的内部智能体平台，Shopify、Block 这些公司都自己搭过，从 Slack 里就能调用。Anthropic 做的事，是把这套东西打包成谁都能直接用的产品。

Angela 的回应：界面确实就是在 Slack 里 @它一下，但真正的重点藏在水面之下，上下文工程、主动性、整套 harness。Andrej Karpathy 的评价很到位，这是一个组织级的 harness。它的体验目标是像同事：你入职一家公司，同事进你的频道，你跟他聊，他会主动把事办了。

对非技术员工，这是巨大的解锁。想知道报销单怎么交，以前要问经理、问同事，跑好几个地方；现在建个频道，@Claude 就行。

再往前看一步：Slack 只是今天的界面，有人在 Teams 协作，有人在 WhatsApp 群里，还有人发邮件。智能体可以占据所有这些人类已经占好的位置。界面会不断更换，水面下的复杂度才是越来越难做、也越来越值钱的部分。

低层 harness 的红利见底了

Sonya 问最佳实践。Katelyn 给的清单很朴素：prompt caching，做，能省很多钱和 token 成本；上下文窗口保持干净，旧的工具调用清出去；有些工具调用用编程方式处理，别把所有东西都灌进上下文；还有 evals，她开玩笑说聊了这么久才第一次说到这个词。

然后是重点：低层 harness 里能榨的油水不多了，真正的创新空间在上面一层。同一个 token 预算，你可以全部拿来执行，也可以分一部分出来：让某个模型反思过去的会话、把经验写进记忆，下一个智能体就能干得更好；用大模型给小模型当顾问，小模型负责执行；或者执行完让一个打分员进来检查，不合格就重来。

Angela 解释了为什么低层在贬值：两年前，harness 本质是脚手架，你得在两边砌墙，模型才能走直线。现在的模型非常可引导（steerable），方向性的东西写进 prompt 就行。如果你的 harness 里还有负责「转向」的部分，可以删了，模型自己会拐弯。harness 剩下的核心工作是让它跑得更久，从 A 到 B，再到 F、到 Z，最后回来汇报。

那要不要做领域专用的 harness？Katelyn 先提醒了一句：大家说 harness 时指的东西五花八门，有人指那个用户、模型、工具来回调的循环，有人指打包好的工具集，一半争论源于定义没对齐。她们的观点是：要，不存在通用 harness。编程是通用能力，但特定领域有一块必须自己定制，模型和你的执行系统之间的校验逻辑。法律、金融这种错一点就有后果的领域，调好这最后一小段，回报巨大，这就是你的产品和别人的产品的差距。至于上下文工程，Angela 觉得有点被过度讨论了：任何 harness 都能处理很多上下文，你有数据，你就有独特优势，如此而已。

从 token 狂飙到 token 理性

Sonya 给当下起了个名字：行业经历了 token maxing 时刻，现在进入 token rationalization 时刻。两位嘉宾都认这个框架。Angela 的判断是，模型能力涨到某个程度，智能这块先打满，下一个维度要么是成本，要么是速度，而且在各种复杂度的任务上都会轮一遍。

她给企业最重要的一条建议：别停用 AI。很多公司的 AI 支出是从影子 IT 长出来的，员工自己想办法装工具，等管理层发现的时候，一半组织已经装上了 Claude Code。这时候一刀切限额是最糟糕的应对。如果 AI 带来了真实回报，发版更快、运营更省，那是收益，不该砍。

正确姿势是搭路由：任务进来，先评估复杂度，难题路由给又大又聪明的模型，简单题给便宜模型。她顺手回应了一个提问：这类路由能力以后会做进 Claude 的体系里，但只限 Claude 家族内部，他们没兴趣帮你把流量路由到别家模型。

Katelyn 补了一个行业观察：曾经大家觉得 harness 和智能体可以跟模型解耦，底下随便换模型，所以路由器很火。现在玩家们上移了一层，Vercel 就把整套 harness 和智能体跟模型家族绑在一起卖。这个方向她认为是对的，harness 应该跟模型家族调到一起。

她还在 Stripe 的经历：那时候大家盯 AWS 账单盯得很紧，有人写了个后台任务没配好，CPU 空转烧钱，护栏系统会发现，然后会有礼貌地请那位工程师把任务关掉。AI 支出也会走到这一天。危险的是简单粗暴设上限，聪明的是事后复盘：同一个结果，你可以用 Opus 跑一整晚，也可以用更聪明的策略，用低得多的成本拿到。

用量结构也在变。编程之外，制造业最近明显抬头，团队里有位 PM 专门飞了趟底特律，去看客户到底在拿 AI 干什么。

明天就能用的几件事

下一阶段 Anthropic 要主攻的，是把「组合策略」做成产品。Angela 举了抓 bug 智能体的例子：一个智能体出去抓 bug，回报有限，常见的两根杠杆是换更大的模型、跑更久。实验发现还有第三根，best-of-N，同时派 N 个智能体再挑最好的，回报高得多。难点在于把它做进生产环境，要搭一堆定制 harness。难而有效的地方，就是超额收益所在，Anthropic 想把这部分变容易。她们内部随口能说出 5 种 token 的工作，开放给生态之后，可能是 10 万种、20 万种组合。她们想服务好的是两类人：企业客户要安全合规，要能把记忆这类组件单独插拔；周末开发者要更开放、更可折腾的东西，最好拿着就能跑。

把这一集的干货收拢成一份清单，明天就能动手：

  • 今天就开 prompt caching，这是最便宜的一笔优化；顺手把上下文窗口里的旧工具调用清出去。
  • 审查自己的 harness，把负责「转向」的脚手架删掉，方向感交给模型，省下的精力先补 evals。
  • 分配 token 预算时留一部分给反思、记忆、顾问和打分员。卡在收益瓶颈时，先试 best-of-N，再考虑换大模型。
  • 做法律、金融这类高风险产品，把模型和执行系统之间的校验逻辑握在自己手里，这是护城河所在。
  • 企业管 AI 支出，别一刀切限额。先搭复杂度路由，难任务给大模型，简单任务给便宜模型，然后像盯 AWS 账单一样事后复盘。
  • 手里有连 API 都没有的老系统，computer use 现在就能跑起来，不用等谁给你开放接口。

结尾用 Angela 的电做比正合适：蜡烛时代能干的事有限，电的价值在于接进一切。平台这层的竞争，比的是谁的插座多，谁能把电接进更多业务。
